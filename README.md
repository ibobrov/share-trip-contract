# ShareTrip Contract Service

## Назначение сервиса

**Contract Service управляет договорными отношениями между платформой ShareTrip и её клиентами и определяет, какие услуги доступны клиенту по договору.**

В минимальной учебной модели клиент — компания, которая использует ShareTrip для организации поездок сотрудников. Договор заключается между компанией и платформой. Договорённости водителя и пассажира об отдельной поездке остаются в области ответственности ShareTrip.

Сервис решает бизнес-проблему ограничения доступа к услугам по договорным условиям. Аутентифицированный пользователь может иметь право работать с поездками, но его компании конкретная услуга может быть недоступна: договор ещё не действует, приостановлен, расторгнут, истёк или не включает эту услугу.

Основной вопрос сервиса: **«Может ли компания использовать конкретную услугу сейчас?»** Остальные сервисы получают готовое решение с причиной отказа и не воспроизводят правила договоров у себя.

## Ответственность сервиса

Contract Service:

- создаёт договор для компании;
- предоставляет договор по идентификатору и активный договор компании;
- управляет статусом договора, включая его активацию;
- хранит срок действия и перечень включённых услуг;
- обеспечивает не более одного активного договора на компанию;
- проверяет доступность конкретной услуги и объясняет отказ;
- владеет собственной схемой хранения и предоставляет другим сервисам API для бизнес-действий.

Сервис принимает решение о **договорной доступности услуги**. Проверка личности и ролей пользователя выполняется Keycloak и слоем авторизации вызывающего сервиса. Даже положительный ответ Contract Service не заменяет проверки прав пользователя и бизнес-правил самой операции.

## Что входит в границу сервиса

### Данные договора

| Данные | Назначение |
| --- | --- |
| Идентификатор договора | Получение и изменение конкретного договора |
| Идентификатор компании (`company_id`) | Связь договора с клиентом платформы |
| Статус | `draft`, `active`, `suspended` или `terminated` |
| Дата начала действия | Момент, с которого договор разрешает пользоваться услугами |
| Дата окончания действия | Момент прекращения доступности; отсутствие даты означает бессрочный договор |
| Услуги договора | Список кодов услуг и их доступность в БД; в API передаются только коды |

Идентификатор компании — внешняя ссылка. Сервис не становится владельцем профиля компании или справочника её сотрудников.

### Статусы договора

| Статус | Значение |
| --- | --- |
| `draft` | Договор создан, но ещё не действует |
| `active` | Договор активен; доступность услуги дополнительно зависит от срока и условий |
| `suspended` | Действие договора временно приостановлено; услуги недоступны |
| `terminated` | Договор расторгнут; услуги недоступны |

В учебной модели подписание рассматривается как бизнес-действие активации договора. Полноценная процедура подписания, электронная подпись и юридический документооборот не моделируются. Допустимые переходы статусов должны быть согласованы с API; произвольная запись статуса в таблицу не является внешним интерфейсом.

### Услуги

| Код | Договорное разрешение |
| --- | --- |
| `trip_creation` | Создавать поездки |
| `trip_publication` | Публиковать поездки |
| `trip_participants` | Добавлять участников поездки |
| `notifications` | Отправлять уведомления |

Contract Service хранит разрешение на услугу, а выполняет её соответствующий сервис. Например, разрешение `notifications` не определяет канал, адресата или содержание уведомления.

## Что не входит в границу сервиса

| Область | Ответственный |
| --- | --- |
| Создание поездок, маршрут, участники, заявки, места и жизненный цикл поездки | ShareTrip |
| Доставка уведомлений, выбор канала, шаблоны и повторные отправки | Notification Service (`sharetrip_notification`) |
| Пользователи, учётные данные и роли | Keycloak |
| Проверка роли пользователя и права выполнить прикладную операцию | Слой авторизации вызывающего сервиса с использованием Keycloak |
| Оплата, счета и расчёты | Вне области ответственности Contract Service |

В Contract Service не должны попадать полные объекты поездок и заявок, списки пассажиров, профили и роли пользователей, пароли, контакты для доставки уведомлений и платёжные реквизиты. Для проверки услуги достаточно идентификатора компании и кода услуги.

В рамках учебного задания также не хранятся история изменений договора и юридические файлы. Ограничения по тарифам, квотам, составу сотрудников и премиальным возможностям могут появиться при развитии продукта, но в минимальную модель не входят.

## Взаимодействие с другими сервисами

| Вызывающий сервис | Зачем обращается |
| --- | --- |
| ShareTrip | Проверяет `trip_creation` перед созданием поездки, `trip_publication` перед публикацией и `trip_participants` перед добавлением участников |
| Notification Service | Может проверять `notifications` перед отправкой уведомления в контексте компании |
| Административный backend, если будет выделен | Создаёт и получает договоры, инициирует подписание/активацию и изменение статуса через защищённый API |

Основной сценарий задания:

1. Пользователь отправляет запрос на создание поездки в ShareTrip.
2. ShareTrip проверяет пользователя и его права и получает идентификатор компании из доверенного контекста.
3. ShareTrip запрашивает в Contract Service доступность `trip_creation` для этой компании.
4. Contract Service проверяет статус договора, срок действия и разрешение услуги.
5. При положительном ответе ShareTrip создаёт поездку по собственным бизнес-правилам. При отрицательном — отклоняет операцию и сообщает причину.

Проверка услуги выполняется отдельным бизнес-методом API. Вызывающий сервис не должен получать строку договора и самостоятельно вычислять разрешение. Метод `get-active` возвращает договор со статусом `active`, если окончание действия отсутствует или ещё не наступило; иначе — `404`. Сам по себе результат не заменяет проверку начала действия и наличия конкретной услуги.

Сервисы не читают и не изменяют БД Contract Service напрямую. Его собственная схема может изменяться при сохранении совместимого API. Доступ к операциям управления договорами защищается на уровне API; это не переносит в Contract Service управление пользователями и ролями.

Если Contract Service недоступен, вызывающий сервис не получает подтверждения доступности услуги. Для минимальной модели защищённая операция не выполняется; техническая ошибка отличается от бизнес-отказа по условиям договора.

## Основные бизнес-правила

1. Договор принадлежит одной компании; компания не может иметь несколько активных договоров.
2. Новый договор создаётся в статусе `draft`. Активировать можно только договор в статусе `draft`; для остальных статусов API возвращает `409`. Активация не должна приводить к появлению второго активного договора компании, в том числе при конкурентных запросах.
3. Допустимы только статусы `draft`, `active`, `suspended` и `terminated`.
4. Только `active` позволяет перейти к проверке срока и услуги. Остальные статусы не предоставляют доступ.
5. Для определённости в проектируемой модели начало срока включительно, окончание исключительно: `starts_at <= now` и `now < expires_at`. Если окончания нет, проверяется только начало. При заданном окончании оно должно быть позже начала; время сравнивается как единый момент независимо от часового пояса клиента.
6. Одна услуга не может дублироваться в рамках одного договора. Услуга доступна, только если включена в договор и её флаг `enabled` равен `true`.
7. Неизвестный код услуги не предоставляет доступ. Поддерживаемый набор ограничен тремя кодами из этого README.
8. Истечение срока само по себе не требует нового статуса: договор со статусом `active` может оказаться просроченным и не предоставлять доступ. Для ограничения «один активный договор» учитывается именно статус, поэтому перед активацией другого договора прежний необходимо вывести из `active`.
9. Разрешение услуги не создаёт поездку, не добавляет участника и не отправляет уведомление. Эти действия и их бизнес-ограничения остаются в вызывающем сервисе.

### Алгоритм проверки доступности услуги

Вход: идентификатор компании и код услуги. Момент проверки определяет Contract Service.

1. Проверить формат входных данных и поддерживаемость кода услуги.
2. Найти договор компании со статусом `active`. Если договоров нет, отказать с причиной `CONTRACT_NOT_FOUND`. Если договоры есть, но активного нет, отказать с причиной `NO_ACTIVE_CONTRACT`; сюда относятся компании только с черновиками, приостановленными или расторгнутыми договорами.
3. Если начало действия ещё не наступило, отказать с причиной `CONTRACT_NOT_STARTED`.
4. Если задано окончание и оно уже наступило, отказать с причиной `CONTRACT_EXPIRED`.
5. Если нужная услуга отсутствует в договоре или её флаг `enabled` равен `false`, отказать с причиной `SERVICE_NOT_ALLOWED`.
6. Иначе вернуть положительный ответ.

Результат бизнес-проверки: `allowed: true` без причины отказа либо `allowed: false` с одним из кодов выше. Если не выполнено несколько условий, возвращается причина первой неуспешной проверки в указанном порядке. Неподдерживаемый код услуги возвращается как ошибка входных данных `UNKNOWN_SERVICE` с HTTP `400`, а некорректный идентификатор — как ошибка валидации с HTTP `400`. HTTP-представление определяется в `api/contract.yaml`.

Все ответы используют сгенерированную оболочку `gen.Response`: `data` содержит результат или `null`, `errors` — массив строк. Бизнес-отказ проверки услуги возвращается с HTTP `200` и пустым `errors`. В ответах договора `expires_at: null` явно обозначает отсутствие окончания; в запросе создания поле можно опустить.

Правило доступности:

```text
allowed = есть договор со статусом active
          И начало действия наступило
          И окончание отсутствует или ещё не наступило
          И услуга включена в договор и enabled = true
```

## Схема хранения

PostgreSQL, миграции:

- `migrations/20261017214934_create_contracts.sql` — договоры;
- `migrations/20261017231853_create_contract_options.sql` — услуги.

| Таблица | Поля | Ограничения |
| --- | --- | --- |
| `contracts` | `id UUID`, `company_id TEXT`, `status TEXT`, `starts_at TIMESTAMPTZ`, `expires_at TIMESTAMPTZ NULL` | PK по `id`, четыре допустимых статуса, окончание строго позже начала |
| `contract_options` | `contract_id UUID`, `code TEXT`, `enabled BOOLEAN NOT NULL DEFAULT TRUE` | Составной PK, FK на договор с `ON DELETE CASCADE`, три допустимых кода услуг |

`id` создаётся через `gen_random_uuid()`, статус по умолчанию — `draft`. `company_id` — непустая строка (например, `company-acme`), которая ссылается на компанию другого домена, поэтому локальной таблицы компаний и межсервисного FK нет. Отсутствие `expires_at` означает бессрочный договор.

Индекс `contracts_company_id_idx` используется для поиска договоров компании. Частичный уникальный индекс `contracts_one_active_per_company_idx` запрещает два договора со статусом `active` у одной компании, включая конкурентную активацию. Составной PK услуг исключает дубли и поддерживает поиск по договору и коду услуги.

Флаг `contract_options.enabled` определяет доступность услуги и по умолчанию равен `true`. В API поле не передаётся; при создании договора перечисленные услуги включены. Проверка доступности учитывает значение флага в БД.

Договор и непустой список его услуг создаются в одной транзакции. Непустоту списка проверяет HTTP-слой через `govalidator`: обычный FK не гарантирует наличие дочерней строки у каждого договора. Активация выполняется условным `UPDATE ... WHERE id = $1 AND status = 'draft'`; переходы статусов не проверяются `CHECK`-ограничением. Конфликт уникального индекса при активации соответствует HTTP `409`.

`get-active` получает договор со статусом `active` и проверяет, что окончание отсутствует или ещё не наступило. Проверка услуги дополнительно учитывает начало действия, наличие кода услуги и `enabled = true`. Текущий момент берётся один раз из runtime через `time.Now().UTC()`; запросов к БД для получения времени нет. Просроченный договор сохраняет статус, пока он явно не изменён; текущий API пока не содержит операции вывода договора из `active`.

## Реализация и локальный запуск

Каркас перенесён из `share-trip-notification`: pgxpool, транзакционная функция, конфигурация окружения, JSON-логгер, request ID, timeout middleware, Compose и структура интеграционных тестов. Предметная логика договоров реализована отдельно.

```text
cmd/contract              сборка зависимостей, запуск и остановка HTTP
internal/api              сгенерированные DTO, HTTP-коды, оболочка ответа
internal/service          границы транзакций и прикладные DTO
internal/domain           проверки договоров, переход статуса, доступность услуг
internal/repository       SQL и pgxpool
internal/app, config      логгер и переменные окружения
internal/observability    request ID, контекстный логгер, таймаут
internal/api_test         HTTP-тесты с временным PostgreSQL
```

OpenAPI находится в `api/contract.yaml`. `make generate` создаёт `gen/openapi.gen.go`; сгенерированный файл не редактируется вручную. Доменные и сервисные типы не зависят от `gen`.

Для каждой операции на слоях API, service и domain объявлены собственные Request и Response. При переходе между слоями поля заполняются явно: общие DTO и преобразования структур целиком не используются. Repository работает с сущностями хранения. Правило линтера S1016 исключено только для этих трёх слоёв, чтобы не заменять явное заполнение DTO приведением типа.

Тесты в `internal/api_test` разнесены по ручкам. В каждом сценарии видны подготовка данных, HTTP-запрос, проверки типизированного ответа и, где нужно, состояния БД. Общий `sendJSONRequest` отвечает только за отправку и чтение JSON, а бизнес-проверки остаются в тестах.

Для запуска нужны Go 1.26 и Docker. Из корня проекта:

```powershell
# Только при первом запуске, если своего .env ещё нет:
Copy-Item .env.example .env
make deps
make up
make migrate-up
make run
```

В `.env` задаются параметры PostgreSQL, `HTTP_PORT`, `LOG_FILE`, `GOOSE_DRIVER` и `GOOSE_DBSTRING`. После изменения параметров БД нужно согласовать с ними `GOOSE_DBSTRING`. Значения по умолчанию в примере: PostgreSQL на порту `6545`, HTTP на `4002`, логи в `deploy/logs/contract.log`. Swagger доступен по адресу `http://localhost:4002/docs`.

```powershell
make generate
make build
make lint
make test
```

`make test` использует отдельный PostgreSQL 16.6 в testcontainers, применяет и откатывает миграции, проверяет HTTP-контракт, валидацию, доступность услуг и конкурентную активацию. Рабочая БД из `.env` в тестах не используется. Проверки точных границ срока выполняются также отдельными доменными тестами.

Создание договора сохраняет договор и услуги атомарно. Активация блокирует строку договора до конца транзакции; уникальный индекс защищает от активации двух разных договоров компании. Валидация разделена на транспортную и бизнес-валидацию:

- **API:** разбирает JSON, проверяет обязательные поля, непустой строковый `company_id`, формат UUID договора и дат, непустой список и допустимые коды услуг. `govalidator/v12` использует теги `valid`, заданные в OpenAPI через `x-oapi-codegen-extra-tags`. Для UUID договора зарегистрирован транспортный валидатор `nonzeroUUID`; формат UUID проверяется при разборе JSON.
- **Domain:** проверяет соотношение дат, дубли услуг, допустимость активации, срок действия и доступность услуги по договору. Отсутствующие поля и формат входных данных здесь не проверяются. Нарушения условий представлены `BusinessValidationError`.

Транспортные ошибки возвращаются до вызова service. У каждого слоя остаются собственные Request/Response с явным заполнением полей.
